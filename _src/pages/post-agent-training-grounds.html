Gold Medals Don't Stack Batteries: Building Training Grounds for AI Agents

The promise behind AI, and especially recursive self-improvement, is a system that learns from its own attempts: a programmer that becomes a better programmer, a researcher that builds better experiments, eventually a generalist that can carry a job through to completion. Where does the measuring stick hang now?

In competitive programming, remarkably high. At the 2025 ICPC World Finals, OpenAI's system solved all 12 problems; Google DeepMind's Gemini Deep Think solved 10 of 12, reaching gold-medal level. The ICPC organisers explicitly distinguish OpenAI's experiment from the more restrictive university championship setting. [1, 2] NVIDIA then reported 535.4 out of 600 on the IOI 2026 problems for a competition-specific Nemotron-3-Ultra-CC system with iterative feedback, above the top human score of 498.27. This was a prospective AI evaluation, not a place in the official human standings. [3]

Research mathematics is moving too. OpenAI's math repository contains model-produced manuscripts and proof artifacts, with verification still at different stages. Formal proofs and unchecked manuscripts deserve different levels of confidence. [4]

I am not saying coding and mathematics aren't useful. But you can't have a nontrivial automorphism for dinner, and a programming medal doesn't align an electrode stack.

A factory gives feedback very differently

Consider battery stacking. A useful system has to combine camera observations, distance measurements, vacuum readings, motion commands, and alignment checks. It needs to recognise an electrode edge, pick the sheet without damaging it, place it within tolerance, and notice when the pickup did not work. A convincing explanation of the trajectory is worth very little if the sheet is still on the table.

This is also a hierarchy of timescales. Camera acquisition and machine control can run far faster than a language model should be asked to deliberate. The agent's job could be to select a procedure, diagnose an abnormal run, or propose a correction; fast controllers still execute bounded motions and enforce machine interlocks. I would start with that division of work, rather than send every camera frame to an LLM.

Long workflows compound uncertainty. An early calibration mistake can survive several apparently successful steps before the final inspection exposes it. METR's task-horizon work measures how agent success changes with the time a human expert needs for a software task. It is a useful measure of sustained autonomy, but it does not measure how long an agent can safely run a battery line. [5]

To improve at this work, an agent needs repeatable attempts, observable consequences, and feedback that distinguishes a good explanation from a good result. More attempts help only when they exercise the right failures and score them correctly.

The old loop, with new plumbing

An environment specifies what the agent can observe, which actions are possible, how those actions change the situation, and how success is scored. Sutton and Barto's agent–environment loop and Szepesvári's Markov decision processes already describe the core interaction. The modern packaging adds containers, tool APIs, files, and execution traces. [6, 7]

One distinction matters: the agent's observation is not necessarily the full state. A photograph may hide a misaligned lower electrode; a successful tool response may not establish that a downstream file is valid. A Markov model assumes the state contains what is needed to predict the next transition. Real agents often have to infer that state from incomplete observations and history.

For a tool-using agent, I would write the environment contract before choosing a training algorithm:

Initial state
The exact files, material batch, calibration, and machine configuration at the start.
Observations and tools
The readings the agent can access and the bounded actions it can request. Permissions are part of the experiment.
Task and budget
A concrete outcome, tolerances, and limits on time, actions, or compute.
Reset
A way to restore the same starting conditions without carrying accidental advantages into the next attempt.
Evidence and scoring
Independent checks of the resulting state, alongside a trace explaining how it was reached.

Gymnasium makes part of this contract explicit through observation and action spaces, reset(), and step(action). Reset returns the first observation; step returns an observation, reward, termination and truncation flags, and auxiliary information. Reaching the goal and exhausting a time budget are different endings. [8]

What changes when the agent learns?

The environment supplies experience. The learning procedure decides what persists from it. That persistent change can live in two places.

Inside the model: training changes its weights. R2E-Gym builds executable software tasks with hybrid verification to train coding agents. On-policy distillation instead trains a student on its own generated sequences using feedback from a teacher, addressing the mismatch between practising on teacher answers and generating its own at deployment. These are different ways of using experience, not interchangeable names for running a test suite. [9, 10]

Around the model: the harness changes what is stored, retrieved, called, and checked. Reflexion keeps verbal feedback in memory for later attempts; Voyager builds a library of executable skills; DSPy optimises language-model pipelines against a metric. A saved procedure can improve an agent without changing the underlying model weights. [11–13]

Meta-Harness goes further by searching over the harness code itself, using previous candidates, scores, and execution traces. Lee and colleagues report a 7.7-point improvement on their online text-classification comparison with four times fewer context tokens, plus results on maths retrieval and agentic coding. It is a reason to measure the complete system: the same model can behave differently when its surrounding software changes. [14]

COS-PLAY, from Xiyang Wu and colleagues, couples a decision agent with an evolving skill bank. Skills are extracted and refined from rollouts, while the decision agent learns to retrieve and use them. Its experiments span six game environments. That gives a concrete example of joint improvement, with demonstrated scope in games rather than battery manufacturing. [15]

A benchmark can supply tasks, tools, and executable checks; using it for training additionally requires a loop that turns attempts and feedback into updates. Evaluation needs separate, held-out tasks. Repeatedly adapting to the same cases can produce a very competent specialist in that particular test suite.

VERA turns recorded work into a place to practise

The October 2026 VERA preprint constructs restartable environments from benchmark trajectories, workspace state, and tool specifications. Generated binary rubrics attach scores to observable evidence. A judge inspects execution and artifacts; container replay checks that the task actually runs. Executable failures override favourable judge scores. Only admitted environments enter the training bank. [16]

Its co-evolution loop attributes failures to model stages or harness skills. Model updates use verified rubric rewards; harness edits face paired development runs with the model frozen. Updates alternate, and rejected candidates do not replace the accepted system. Stage-wise evaluation helps locate failures; end-to-end evaluation checks the complete workflow. The reported gains concern automation and medical-research benchmarks. [16]

I find the separation of proposals from acceptance especially useful. An agent may propose its next skill or training stage, while independent execution decides whether the change helps. That is a much more inspectable improvement process than keeping every edit because the agent produced a persuasive rationale.

A stack that passes the test can still be wrong

Here is a thought experiment for a stacking environment. The task is to place several electrode and separator layers within a specified tolerance. The simulator records every placement, pickup confirmation, sensor reading, and final inspection. Those records make several rewards possible:

  • “The agent says it finished.” Cheap to score, but rewards a statement about the work.
  • “The final photograph looks aligned.” Better evidence, but may miss a shifted layer beneath the top sheet.
  • “Each placement passed independent measurement, and the final stack passed inspection.” More informative, with higher instrumentation and verification costs.

A faster agent can exploit an incomplete check without improving the stack. It might omit an inspection, accept stale measurements, or rewrite a result file. The verifier must read evidence the agent cannot simply overwrite. If the simulator itself guarantees perfect pickup, no amount of training inside it will teach recovery from a failed pickup.

Stage rewards need care too. Rewarding a particular trajectory can punish a valid alternative. I would score physical constraints and useful artifacts, allowing several ways to satisfy them, and keep the final outcome as an independent check. A diagnostic report is helpful because it explains a failure; it must not turn a failed stack into a successful one.

How I would build the first manufacturing environment

I would begin with a bounded task: diagnose and recover a simulated failed pickup. The agent receives a log, a camera snapshot, vacuum readings, and a small set of authorised tools. It must identify whether the sheet was picked up, choose a permitted recovery, and produce a traceable report. Motion limits and stop conditions belong in the tool implementation.

Early versions can replay recorded sensor data and use a simplified machine model. That is enough to test tool use, evidence handling, and diagnosis, while leaving contact mechanics and real machine qualification unresolved. A replay cannot tell us what would have happened under an action absent from the recording; a simulator must supply that transition, with its assumptions made explicit.

The curriculum would change one difficulty at a time: a clean failed pickup, noisy pressure readings, a delayed camera frame, a stale calibration, then combinations. Successful runs and recoverable failures both belong in the set. A task that always ends in a fault teaches a different prior from a production line where most cycles work.

I would then compare three systems on the same unseen cases: the starting agent, a revised harness around the same frozen model, and a trained model using the same fixed harness. Only after those comparisons would I combine the accepted changes. That makes it possible to ask whether a gain came from learned behaviour, a useful procedure, or simply a more generous tool.

My main measures would be accepted recoveries per attempt, correct fault attribution, false-success reports, time and tool calls per accepted recovery, and performance on withheld batches or fault combinations. A higher rubric score is encouraging when it moves these outcomes too. Fresh tasks, fixed budgets, and a verifier kept outside the agent's editing permissions make that claim testable.

The step from replay to a test stand is a separate engineering milestone. A model that handles a simulated vacuum fault still has to cope with actual sensor timing, sheet variability, and equipment behaviour. I would move through offline evaluation, shadow operation, and bounded test-stand trials before allowing a validated procedure to influence production.

The scarce resource is useful feedback

What makes these environments valuable is the number of reliable learning cycles they enable: start from a known state, try something, inspect the consequences, accept or reject an update, and repeat on a fresh case. Faster resets and better evidence can make those cycles cheaper. A fragile simulator or an easily fooled score can make thousands of cycles teach the wrong habit.

For manufacturing, the interesting question is whether we can build enough varied, faithful practice tasks to improve useful procedures before consuming material and machine time. Code and maths benefit from unusually strong checks. Bringing comparable feedback to experiments, diagnostics, and process operations is a substantial part of the work still ahead.

An agent that says “I learned from that” has supplied another sentence. An agent that handles the next unfamiliar failed pickup correctly, with the evidence to show it, has supplied something I can measure.
