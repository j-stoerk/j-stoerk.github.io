Turning my research into operating skills: an offline DisCo dry run

There is a particular kind of déjà vu in asking an AI agent to help with research. It can explain a model, derive an equation, and write a training loop. Then, next week, it has to rediscover which metric matters, which plot catches a broken assumption, and why one result should not be called a validation.

DisCo proposes a practical fix: distill the operating knowledge around a source into a small graph of reusable skills. A Creator scopes a source, gathers evidence, builds the skills, then verifies them. A Researcher later loads only the relevant parts. I wanted to see what that would look like on my own work, rather than another generic repository.

What I could actually run. I tried to launch the DisCo Creator CLI, but this environment could not fetch its package from the npm registry (`ENOTCACHED`), and no model-provider key was configured in the shell. So this is an offline Creator-style dry run over the files already in my portfolio, not a DisCo-generated or DisCo-verified result. The distinction matters: I can inspect whether the source contains enough evidence to make useful skills, but I cannot claim the agent produced or executed them.

Two anchors, one small graph

I chose two task-agnostic anchors from the portfolio. The first is my calendering work: why electrode through-plane thermal conductivity falls and then rises with compaction, and how a compression-aware closure captures that U-shape. The second is my continual-learning work: how task interference relates to forgetting, and how IGFA gates or projects updates to protect earlier tasks.

For each, I used the blog post as the readable map and the linked draft PDF as the primary local evidence. The posts are useful, but they also include interactive figures. Those figures are not all experimental results: for example, the calendering curves and the two-dimensional IGFA widget are explicitly schematic. A skill that does not preserve that distinction would make the portfolio less reliable, not more.

The resulting candidate graph has a router and two operating notes. The router asks the agent to identify which research thread the task concerns, open only that skill, and keep claims separate if a task crosses both domains. That is a deliberately small graph: the GLEE agent post is another distinct workflow, and mixing it in would add breadth without enough evidence for this first pass.

What the skills preserve

The calendering note starts with the measurement target. The draft calibrates apparent through-plane coating conductivity derived from laser-flash analysis after current-collector subtraction. It reports four electrode families over 27 calendering states. A reusable procedure should keep the target and preprocessing fixed, compare the staged closures, separate in-sample from held-out error, and inspect parameter identifiability before interpreting fitted values.

That last check changes how the headline result should travel. The draft reports 4.5% in-sample MAPE and 7.8% leave-one-state-out error. It also says the graphite reorientation explanation is not uniquely identified from conductivity alone; same-sheet XRD texture is proposed as a way to distinguish it from a contact-only account. A future agent should carry those boundaries with the number, not just repeat the number.

The IGFA note begins with a regime check. In the frozen-feature setting, the draft's interference functional gives an exact expression for forgetting. When features move during end-to-end training, it becomes an approximation. The skill then asks for the task order, feature extractor, seeds, baselines, accuracy, and forgetting together. It also records the cost of protection: projecting a gradient can slow learning, while repeated protection can consume the available subspace.

It also prevents a particularly easy mistake. The interactive widget uses a made-up two-dimensional covariance to show how a gate behaves. The draft separately reports Rotated-Digits benchmark outcomes over five seeds. An agent should not use the widget as a benchmark, or turn the reported result into a claim of independent reproduction.

The verification gap is the result

The most useful finding from this exercise was what the portfolio cannot yet do. It contains posts and draft PDFs, but not the original calendering data, fit code, pinned environment, continual-learning benchmark implementation, or per-seed outputs. I could write sensible procedures and evidence checks. I could not wrap the actual workflows in stable scripts or run assertion-backed cases against them.

I recorded that as a gap instead of filling it with invented commands. The candidate skills say exactly which inputs are missing, which reported results remain manuscript claims, and which figures are illustrative. They are useful operating notes for reading and planning. They are not executable research skills yet.

This is where the distinction between a skill library and a stack of summaries becomes concrete. A summary says what the paper found. An operating skill also says what to load, what to run, which assumption controls the interpretation, what would count as a check, and when the evidence is insufficient. If the data and implementation are not available, “blocked” is part of the useful output.

What I would do with a working Creator

Once the CLI and provider are available, the next pass is straightforward: give Creator the source repositories alongside these papers, have it verify the two graphs against small native examples, then open a fresh Researcher session with one narrow task per graph. For calendering, that could be a held-out-state prediction with the preprocessing recorded. For IGFA, it could be a matched-seed benchmark rerun with the feature regime and buffer budget fixed.

Until then, this dry run still paid for itself. It exposed the difference between having research conclusions in a portfolio and having the materials needed to repeat the work. The first is enough to explain a result. The second is what lets an agent help produce the next one.
